# Self-healing: por que o Pod volta?

Esta apostila acompanha a primeira lição. Você pode consultá-la antes, durante ou depois da atividade — não precisa terminar a leitura para experimentar o cluster.

<section id="o-que-voce-vai-entender">

## O que você vai entender

- Como o Kubernetes compara **desired state** e **actual state** continuamente.
- Por que Deployment, ReplicaSet e Pod têm responsabilidades diferentes.
- O que acontece entre a criação de um Pod e o momento em que ele fica Ready.

</section>

<section id="conceitos">

## Conceitos

<h3 id="desired-state-e-actual-state">Desired state e actual state</h3>

Pense em um termostato. Você escolhe 22 °C: esse é o **desired state**. O sensor mede 19 °C: esse é o **actual state**. O aparelho não precisa de uma ordem sua a cada segundo; ele observa a diferença e liga o aquecimento até os dois valores coincidirem.

No Kubernetes, o manifesto declara o que você quer. Os controllers observam o que existe no cluster e agem quando há diferença. Se você declarou três réplicas e só existem duas, falta uma. Se existem quatro, sobra uma.

<DesiredActualDiagram />

<Callout>Self-healing não significa “consertar o mesmo container”. Muitas vezes significa descartar uma instância e criar outra que satisfaça o estado declarado.</Callout>

<h3 id="deployment-replicaset-e-pods">Deployment, ReplicaSet e Pods</h3>

Um **Pod** é a menor unidade executável do Kubernetes. Nesta lição, cada Pod contém uma instância do backend.

Um **ReplicaSet** mantém uma quantidade estável de Pods equivalentes. Ele conta os Pods que correspondem ao seu selector e cria ou remove a diferença até chegar ao número Desired.

Um **Deployment** descreve como a aplicação deve ser implantada e atualizada. Ele cria e administra ReplicaSets, permitindo rollout e rollback. O Deployment não substitui o Pod diretamente: ele gerencia o ReplicaSet, e o ReplicaSet gerencia os Pods.

<OwnershipDiagram />

Essa cadeia aparece no campo **`metadata.ownerReferences`**. Um Pod aponta para o ReplicaSet que o possui; o ReplicaSet aponta para o Deployment. Essa relação ajuda os controllers e a coleta de lixo do cluster a entenderem quem responde por cada recurso.

<h3 id="ciclo-de-vida-do-pod">Ciclo de vida do Pod</h3>

Nesta simulação, você acompanha quatro momentos:

1. **Pending:** o Pod foi aceito, mas ainda não começou a executar.
2. **ContainerCreating:** o **scheduler** já escolheu um node e o **kubelet** prepara o container, incluindo imagem, rede e volumes.
3. **Running:** o container principal está executando.
4. **Ready:** a **readiness probe** passou e o Pod pode receber tráfego de um Service.

<PodLifecycleDiagram />

**Running não é o mesmo que Ready.** Um processo pode estar de pé e ainda estar carregando dados, esperando uma dependência ou falhando na readiness probe. O Service só deve enviar tráfego quando o Pod estiver Ready.

<h3 id="loop-de-reconciliacao">O loop de reconciliação</h3>

Um controller repete três passos:

1. **Observar:** lê o desired state e o actual state.
2. **Comparar:** calcula a diferença entre eles.
3. **Agir:** cria, atualiza ou remove recursos para reduzir essa diferença.

<ReconciliationDiagram />

Ao apagar um Pod, você altera o actual state, não o desired state. O ReplicaSet continua desejando três réplicas. Na observação seguinte ele encontra apenas duas e cria um substituto.

</section>

<section id="no-mundo-real">

## No mundo real

### O manifesto `backend.yaml`

Este é o mesmo arquivo disponível no terminal da lição, com um comentário antes de cada parte:

```yaml
# Usa a API estável para workloads.
apiVersion: apps/v1
# Declara um Deployment.
kind: Deployment
metadata:
  # Nome do Deployment (e prefixo dos ReplicaSets e Pods).
  name: backend
# Daqui para baixo, o estado desejado.
spec:
  # Quantos Pods equivalentes você quer.
  replicas: 3
  # Pods com app=backend pertencem a este Deployment.
  selector:
    matchLabels:
      app: backend
  # O modelo usado para criar cada Pod.
  template:
    metadata:
      # Labels de cada Pod novo — precisam combinar
      # com o selector acima.
      labels:
        app: backend
    spec:
      containers:
        # Container principal e a imagem (com versão).
        - name: backend
          image: ghcr.io/kubelearn/backend:1.4
          # Pronto só quando GET /healthz na porta
          # 8080 responder com sucesso.
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
```

O selector e as labels do template precisam combinar. Caso contrário, o Deployment criaria Pods que seu ReplicaSet não consegue reconhecer como próprios.

### Os comandos da atividade

```console
kubectl apply -f backend.yaml
```

Cria o Deployment ou atualiza o existente para corresponder ao arquivo. O Deployment cria um ReplicaSet; o ReplicaSet cria os Pods.

```console
kubectl get pods
```

Lista os Pods e mostra colunas como `READY`, `STATUS`, `RESTARTS` e `AGE`. Use `kubectl get pods -o wide` para ver também IP e node.

```console
kubectl delete pod backend-...
```

Solicita a exclusão de um Pod específico. Como o Deployment continua declarando três réplicas, o ReplicaSet cria outro Pod. Para mudar a quantidade de forma duradoura, altere o desired state do Deployment.

```console
kubectl describe pod backend-...
```

Mostra detalhes do recurso e seus eventos recentes. É útil para descobrir onde o Pod foi agendado, por que ainda não está Ready ou qual controller é seu dono.

</section>

<section id="o-que-simplificamos">

## O que simplificamos

- No cluster real, muitas dessas mudanças levam milissegundos. A simulação desacelera o tempo para que cada etapa fique visível.
- O ReplicaSet cria o substituto assim que percebe a falta; ele não espera o Pod antigo terminar de encerrar.
- Os “slots” desenhados no palco são apenas didáticos. O Kubernetes não reserva posições visuais para réplicas.
- A simulação mostra os componentes importantes para a lição, mas omite detalhes de rede, armazenamento, admission e outros controllers.

</section>

<section id="erros-comuns">

## Erros comuns

### Apagar um Pod achando que ele não volta

Se o Pod pertence a um ReplicaSet e o desired state não mudou, outro será criado. Para reduzir a aplicação, altere as réplicas do Deployment.

### Editar diretamente um Pod gerenciado

O Pod novo será criado a partir do template do Deployment, não das mudanças manuais feitas no Pod antigo. Altere o template do Deployment para tornar a mudança duradoura.

### Confundir Deployment com ReplicaSet

O Deployment cuida de versões, rollout e rollback. Cada versão normalmente corresponde a um ReplicaSet; o ReplicaSet cuida da quantidade de Pods daquela versão.

### Achar que Running significa pronto

Running só informa que o container está executando. Ready depende da readiness probe e determina se o Pod pode receber tráfego.
