# Falhas e rollbacks: errar sem derrubar ninguém

Esta apostila acompanha a lição 6. Na atividade você publicou uma versão que quebrava ao iniciar, e os usuários nem perceberam. Aqui está o mecanismo que garantiu isso, como investigar o erro e as duas saídas possíveis: voltar ou corrigir.

<section id="o-que-voce-vai-entender">

## O que você vai entender

- Como um **rolling update** troca os Pods de versão, e por que a **readiness** o torna seguro.
- O que significa **CrashLoopBackOff** e como descobrir a causa.
- Quando fazer **rollback** e quando **corrigir para frente**.

</section>

<section id="conceitos">

## Conceitos

<h3 id="rolling-update">Rolling update</h3>

Toda mudança no **template** de Pods de um Deployment (a imagem, por exemplo) gera uma nova **revisão** e um **ReplicaSet novo**. O Deployment então move as réplicas aos poucos, do ReplicaSet antigo para o novo, respeitando dois limites:

- **maxSurge**: quantos Pods **a mais** que o desejado podem existir durante a troca (padrão 25%, arredondado para cima);
- **maxUnavailable**: quantos Pods **a menos** que o desejado podem estar indisponíveis (padrão 25%, arredondado para baixo).

Com 3 réplicas: 25% de 3 é 0,75. Para cima, o surge vira **1**; para baixo, o unavailable vira **0**. Ou seja: pode haver 1 Pod extra, e **nenhum** Pod pronto pode faltar.

<h3 id="readiness-e-o-portao">A readiness é o portão</h3>

O Deployment só encerra um Pod antigo quando um novo fica **Ready**. Um Pod novo que nunca fica Ready nunca “libera” a saída de um antigo. Por isso a v1.5 não derrubou nada: ela travou no primeiro Pod extra, e os três Pods da v1.4 continuaram atendendo.

Sem uma readiness probe, “Ready” significaria apenas “o container iniciou” — e uma versão que inicia mas não funciona poderia, sim, substituir todos os Pods bons.

<h3 id="crashloopbackoff">CrashLoopBackOff</h3>

Quando o container encerra com erro, o kubelet o reinicia — dentro do mesmo Pod, no mesmo node. Para não ficar reiniciando sem parar, ele espera cada vez mais entre as tentativas: 10 s, 20 s, 40 s… até o limite de **5 minutos**. Se o container ficar 10 minutos rodando sem problemas, essa espera volta ao início.

No `kubectl get pods`, você vê o ciclo:

- `STATUS` alterna entre **Error** (acabou de cair) e **CrashLoopBackOff** (esperando para tentar de novo);
- `RESTARTS` só cresce.

CrashLoopBackOff não é um problema do cluster: é o cluster avisando que **o seu container não para de pé**. A causa quase sempre está nos logs.

<h3 id="rollout-travado">Rollout travado</h3>

O Deployment não desiste sozinho. Depois de `progressDeadlineSeconds` (600 segundos por padrão) sem progresso, ele marca a condição `Progressing=False` com o motivo **ProgressDeadlineExceeded**, mas **continua tentando**. Não há rollback automático: decidir o que fazer é com você.

<h3 id="controlando-o-rollout">Reiniciar, pausar e retomar</h3>

`kubectl rollout restart` inicia uma nova substituição gradual sem exigir uma imagem diferente. É útil quando a configuração externa mudou e os Pods precisam nascer de novo, mas continua sendo um rollout: readiness e limites de disponibilidade ainda importam.

`kubectl rollout pause` congela novos rollouts do Deployment. Mudanças feitas no template durante a pausa ficam registradas, mas não criam ReplicaSets até `kubectl rollout resume`; ao retomar, elas saem juntas. Um Deployment pausado também não pode receber rollback até ser retomado.

<h3 id="rollback">Rollback</h3>

O ReplicaSet antigo não foi apagado: ficou guardado com 0 réplicas (o Deployment guarda até 10 revisões antigas, por padrão). Um **rollback** devolve o template anterior ao Deployment, que reaproveita aquele ReplicaSet — escalando-o de volta e o quebrado para zero. Por isso é rápido.

O rollback gera uma **revisão nova** (no histórico, a v1.4 reaparece com um número maior) e devolve **apenas o template de Pods**. Ele não desfaz migrações de banco, mudanças em ConfigMaps nem nada fora do Deployment.

<h3 id="corrigir-para-frente">Corrigir para frente</h3>

O rollback tira os usuários do perigo, mas a v1.5 continua quebrada. Os logs da lição mostravam o motivo:

```text
panic: config: required environment variable DATABASE_URL is not set
```

A correção é entregar essa configuração ao container e publicar de novo. Com a variável presente, a v1.5 ficaria Ready e o rolling update concluiria normalmente.

<Callout>Rollback é para **parar o estrago**; a correção é o que resolve. Em produção, geralmente se faz os dois: rollback primeiro, correção com calma depois.</Callout>

<section id="no-mundo-real">

## No mundo real

### Os comandos da atividade

```console
kubectl set image deployment/backend backend=ghcr.io/kubelearn/backend:1.5
```

Troca a imagem do container `backend`. É uma mudança de template, então começa um rollout.

```console
kubectl rollout status deployment/backend
```

Acompanha o rollout e espera ele terminar — ou mostra onde parou.

```console
kubectl logs backend-…
kubectl logs backend-… --previous
```

Mostram a saída do container. Com `--previous`, a do container **anterior**, que acabou de cair — muitas vezes é ali que está a mensagem de erro.

```console
kubectl describe pod backend-…
```

Em `Last State`, mostra `Terminated`, o motivo e o **código de saída**; em `Restart Count`, quantas vezes já reiniciou; em `Events`, os avisos de back-off.

```console
kubectl rollout undo deployment/backend
kubectl rollout history deployment/backend
kubectl rollout undo deployment/backend --to-revision=1
```

Desfaz para a revisão anterior, lista o histórico e volta a uma revisão específica. Consulte o histórico antes: `--to-revision=1` escolhe a revisão 1, não “uma revisão para trás”.

### Reiniciando ou agrupando mudanças

```console
kubectl rollout restart deployment/backend
```

Troca todos os Pods gradualmente sem mudar a imagem. Para acumular mudanças no template e disparar um único rollout:

```console
kubectl rollout pause deployment/backend
kubectl set image deployment/backend backend=ghcr.io/kubelearn/backend:1.5
kubectl rollout resume deployment/backend
```

No terminal da simulação, `rollout history` identifica também uma revisão criada por `rollout restart`. Para inspecionar qualquer um desses comandos sem alterar o cluster:

```console
explicar kubectl rollout undo deployment/backend --to-revision=1
```

`explicar` é um recurso didático do KubeLearn e não executa o comando.

### Corrigindo para frente

Um ConfigMap guarda a configuração:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: backend-config
data:
  DATABASE_URL: postgres://db:5432/app
```

E o container lê dele:

```yaml
containers:
  - name: backend
    image: ghcr.io/kubelearn/backend:1.5
    env:
      # a variável que faltava, vinda do ConfigMap
      - name: DATABASE_URL
        valueFrom:
          configMapKeyRef:
            name: backend-config
            key: DATABASE_URL
```

Se o valor tiver senha, use um **Secret** (`secretKeyRef`) no lugar do ConfigMap.

<section id="o-que-simplificamos">

## O que simplificamos

- O back-off da simulação vai de 1,5 s a 8 s; no cluster real, de 10 s a 5 minutos.
- O rollout é marcado como “travado” logo no primeiro crash. No real, isso só aparece no status depois do `progressDeadlineSeconds`.
- Os logs são fixos e ilustrativos.
- O restart usa um marcador interno no template; no cluster real, o kubectl registra o momento do restart em uma annotation do template.
- Não há ConfigMaps na simulação, então a correção para frente fica só nesta apostila.

</section>

<section id="erros-comuns">

## Erros comuns

### Achar que CrashLoopBackOff é problema do Kubernetes

O cluster está fazendo o trabalho dele: reiniciar. A falha é do container — configuração, dependência ou bug.

### Ler os logs do container errado

Logo depois de um reinício, `kubectl logs` pode mostrar só o início do container novo. A mensagem do erro está no anterior: use `--previous`.

### Achar que o rollback desfaz tudo

Ele só volta o template de Pods. Dados, migrações e configurações externas continuam como estão.

### Fazer rollback e esquecer o arquivo

Se o manifesto no Git ainda aponta para a v1.5, o próximo deploy quebra de novo. Leve a decisão para o arquivo.

### Liveness probe agressiva demais

Uma liveness probe que falha durante um início lento faz o kubelet matar o container repetidamente — e gera um CrashLoopBackOff que não existiria sem ela.
