# Depuração: quando tudo roda e nada funciona

Esta apostila acompanha a lição 5. Ela ensina um **método** para investigar Services, e não só a resposta daquele exercício. Se ainda não terminou a atividade, leia os conceitos e o checklist; a solução aparece só em “No mundo real”.

<section id="o-que-voce-vai-entender">

## O que você vai entender

- Como investigar com método — sintoma, hipótese, evidência, correção — em vez de sair tentando coisas.
- O caminho de uma requisição até um Pod, e em que ponto cada problema comum aparece.
- Quais comandos respondem a cada pergunta, e como corrigir sem criar um problema novo.

</section>

<section id="conceitos">

## Conceitos

<h3 id="metodo">Um método, não um palpite</h3>

1. **Sintoma:** o que exatamente falha? (“as requisições ao backend falham; os Pods estão Running e Ready”.)
2. **Hipótese:** qual parte do caminho pode explicar isso?
3. **Evidência:** que comando confirma ou derruba a hipótese?
4. **Correção:** mude **uma** coisa, na fonte certa, e verifique de novo.

Reiniciar Pods “para ver se resolve” pula os passos 2 e 3. Quando funciona, você não sabe por quê; quando não funciona, perdeu o estado que ajudaria a entender.

<h3 id="caminho-da-requisicao">O caminho de uma requisição</h3>

Uma requisição a `http://backend` passa por várias etapas, e cada uma pode falhar:

1. o nome `backend` é resolvido pelo DNS do cluster para o IP do Service;
2. o kube-proxy encaminha a conexão para um dos **endpoints**;
3. os endpoints são os Pods que **combinam com o selector** e estão **Ready**;
4. a conexão chega ao Pod no **targetPort**, onde o container precisa estar escutando.

Siga esse caminho na ordem. O primeiro elo quebrado é onde o problema está.

<DebugPathDiagram />

<h3 id="sintomas">Lendo os sintomas</h3>

| O que você vê | Causa mais provável |
|---|---|
| Endpoints vazios e Pods **Ready** | o selector do Service não combina com as labels dos Pods |
| Endpoints vazios e Pods **não Ready** | a readiness probe está falhando |
| Endpoints preenchidos, conexão recusada | `targetPort` errado, ou o app não escuta nessa porta |
| Funciona por IP do Service, não pelo nome | DNS, ou namespace diferente |

Sem endpoints, a conexão ao Service costuma falhar na hora. Se houver um Ingress ou um gateway na frente, ele normalmente responde **503 Service Unavailable** — o mesmo sintoma da lição.

<Callout>Um Service sem endpoints é um dos problemas mais comuns em clusters novos. A documentação oficial tem um guia inteiro só sobre isso, seguindo exatamente esse caminho.</Callout>

<section id="no-mundo-real">

## No mundo real

### A investigação da lição, comando a comando

```console
kubectl describe service backend
```

Mostra `Selector: app=api` e `Endpoints: <none>`. O Service existe, mas não encontra ninguém.

```console
kubectl get pods -l app=api
```

Usa o **mesmo selector** do Service. Resposta: `No resources found`. Nenhum Pod tem essa label.

```console
kubectl get pods --show-labels
```

Os Pods estão Running, Ready e têm `app=backend`. Hipótese confirmada: o selector e as labels discordam.

### Corrigindo no lugar certo

Os Pods estão certos: o template do Deployment diz `app: backend`. Quem está errado é o Service.

```console
kubectl set selector service backend app=backend
```

Substitui o selector do Service inteiro. Os endpoints aparecem na hora, sem reiniciar nada.

Num time de verdade, a correção definitiva vai para o **arquivo versionado** do Service. Sem isso, o próximo `kubectl apply` traz o `app=api` de volta.

### Outras ferramentas úteis

```console
kubectl port-forward service/backend 8080:80
```

Abre um túnel do seu computador até o Service: `http://localhost:8080` passa a chegar nele. Bom para testar sem expor nada.

```console
kubectl run teste --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- http://backend
```

Testa de dentro do cluster, passando pelo DNS e pelo kube-proxy como qualquer outro Pod faria.

Se a dúvida for só a resolução do nome, isole a primeira etapa:

```console
kubectl run dns --rm -it --image=busybox:1.36 --restart=Never -- nslookup backend
```

No terminal da simulação, os dois testes acima funcionam. Se quiser entender cada argumento antes de executar, use:

```console
explicar kubectl run teste --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- http://backend
```

`explicar` é uma ajuda didática do KubeLearn: ele decompõe o comando, mas não o executa. No kubectl real, `kubectl explain` tem outro papel — consultar os campos e a estrutura dos recursos.

</section>

<section id="o-que-simplificamos">

## O que simplificamos

- O exercício tem uma única causa. Na prática, NetworkPolicies, DNS, namespaces e o próprio app também entram na lista de suspeitos.
- O “503” aparece no próprio Service, para o sintoma ficar visível. Sem um Ingress na frente, um cliente real normalmente veria a conexão falhar.
- `kubectl run` simula `wget`, `curl` e `nslookup` de dentro do cluster. `port-forward` e um shell interativo ainda não são simulados.

</section>

<section id="erros-comuns">

## Erros comuns

### Trocar as labels dos Pods em vez do selector

Parece resolver, mas os Pods são gerenciados: o ReplicaSet os libera e cria substitutos com as labels do template, que continuam sem combinar (lição 4). Corrija quem está errado.

### Reiniciar Pods para “ver se volta”

Nada no Pod estava errado. Reiniciar não muda o selector do Service, e ainda gera ruído na investigação.

### Corrigir só no cluster

Uma correção feita com `kubectl set` ou `kubectl edit` some no próximo deploy se o arquivo continuar errado.

### Procurar no namespace errado

`kubectl get pods` lista só o namespace atual. Se o Service está em `prod` e você olha `default`, tudo parece vazio. Use `-n prod`.
