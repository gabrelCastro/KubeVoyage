# Secrets: separado não é o mesmo que protegido

Esta apostila acompanha a lição 8. Na atividade, a v1.5 da lição 6 — que quebrava por falta de `DATABASE_URL` — finalmente rodou: a senha veio de um Secret. E você descobriu, com um `base64 -d`, o que um Secret faz e o que ele não faz.

<section id="o-que-voce-vai-entender">

## O que você vai entender

- O que é um **Secret** e como ele chega ao container.
- Por que **base64** não é criptografia, e quem consegue ler um Secret.
- O que de fato protege um Secret num cluster de verdade.

</section>

<section id="conceitos">

## Conceitos

<h3 id="secret">Secret</h3>

Um **Secret** guarda dados sensíveis — senhas, tokens, chaves — separados da imagem e dos manifestos da aplicação. Ele funciona como um ConfigMap: o container recebe os valores como variáveis de ambiente (ou como arquivos, num volume).

```yaml
envFrom:
  - secretRef:
      name: db-credentials
```

Assim como na lição 7, se o Secret não existe, o container não é criado: o Pod fica em `CreateContainerConfigError`. E, como variável de ambiente, o valor é lido só quando o container inicia.

<h3 id="base64">base64 é só uma codificação</h3>

No objeto que a API devolve, os valores de um Secret aparecem em **base64** — a documentação exige que tudo em `data` seja uma string base64. Isso existe para guardar qualquer byte (inclusive binários) como texto, não para esconder: não há chave, e qualquer um decodifica.

```bash
kubectl get secret db-credentials -o jsonpath='{.data.DATABASE_URL}' | base64 -d
```

O `kubectl describe` mostra só o tamanho de cada valor, para ele não aparecer por acidente num terminal ou numa gravação de tela. É uma gentileza, não uma barreira.

<h3 id="quem-le-um-secret">Quem consegue ler um Secret</h3>

A documentação é clara: por padrão, os Secrets ficam **sem criptografia** no etcd, o banco de dados do cluster. Quem tem acesso à API pode ler ou alterar um Secret — e quem tem acesso ao etcd também. E mais: quem pode **criar um Pod** num namespace consegue ler qualquer Secret desse namespace, montando-o no próprio Pod.

Então o que um Secret oferece é um **objeto separado**, que pode ter permissões separadas. A proteção de verdade vem de outras peças.

<h3 id="protegendo">O que protege um Secret</h3>

- **RBAC**: só dar permissão de `get`/`list` em Secrets para quem realmente precisa — e lembrar que criar Pods também dá acesso indireto.
- **Criptografia em repouso**: configurar o API server para criptografar os Secrets antes de gravá-los no etcd.
- **Gerenciadores externos**: soluções como Vault ou os cofres dos provedores de nuvem, integrados ao cluster, para os dados mais sensíveis.

</section>

<section id="no-mundo-real">

## No mundo real

### Os comandos da atividade

```bash
kubectl create secret generic db-credentials \
  --from-literal=DATABASE_URL=postgres://app:s3cret@db:5432/app
kubectl describe secret db-credentials        # DATABASE_URL: 33 bytes
kubectl get secret db-credentials -o yaml     # data: DATABASE_URL: cG9zdGdyZXM6...
kubectl get secret db-credentials -o jsonpath='{.data.DATABASE_URL}' | base64 -d
kubectl apply -f backend-secret.yaml
```

### Escrevendo Secrets em YAML

Para não codificar à mão, use `stringData`: você escreve em texto puro e a API guarda em base64.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
stringData:
  DATABASE_URL: postgres://app:s3cret@db:5432/app
```

<Callout title="Não versione Secrets em texto puro">
  Um YAML com `stringData` (ou com `data` em base64) no repositório é uma senha publicada. Times usam ferramentas que guardam o Secret criptografado no Git e só o decifram dentro do cluster — ou geram o Secret a partir de um cofre externo.
</Callout>

### Tipos de Secret

O tipo padrão é `Opaque`: chaves e valores quaisquer. Há tipos com formato definido, como `kubernetes.io/tls` (certificado e chave) e `kubernetes.io/dockerconfigjson` (credenciais de registry, usadas para baixar imagens privadas).

</section>

<section id="o-que-simplificamos">

## O que simplificamos

- Só existe `kubectl create secret generic` com `--from-literal`. No kubectl real também há `--from-file`, e os tipos `tls` e `docker-registry`.
- Os Secrets entram só por `envFrom`. Não simulamos volumes de Secret, `secretKeyRef` (uma chave por vez) nem `imagePullSecrets`.
- Aqui não há RBAC: qualquer comando enxerga tudo, como um administrador do cluster.
- O `-o jsonpath` daqui entende caminhos simples (`{.data.CHAVE}`, `{.items[*].metadata.name}`), não a linguagem completa.

</section>

<section id="erros-comuns">

## Erros comuns

### Achar que base64 protege

Não protege. Se alguém consegue ler o objeto, consegue ler o valor. A proteção está em quem pode ler o objeto.

### Colocar senha em ConfigMap

Funciona tecnicamente — e perde a chance de dar permissões separadas, de criptografar em repouso e de evitar que o valor apareça em `describe`. Senhas vão em Secrets.

### Esquecer do acesso indireto

Negar `get secrets` a um usuário que pode criar Pods não basta: ele cria um Pod que monta o Secret e lê o valor de dentro.

### Mudar o Secret e esperar que o app perceba

Como na lição 7: variável de ambiente é lida quando o container inicia. Depois de trocar uma senha, os Pods precisam ser recriados (`kubectl rollout restart`).

</section>

<section id="para-ir-alem">

## Para ir além

- **Criptografia em repouso** é configurada no API server, com um provedor de chaves (de preferência um KMS externo).
- **Secrets imutáveis** (`immutable: true`), como os ConfigMaps imutáveis, não podem ser alterados depois de criados.
- **Projetos como External Secrets e Sealed Secrets** ligam o cluster a cofres externos ou permitem versionar Secrets criptografados.
- [Secrets — conceito](https://kubernetes.io/docs/concepts/configuration/secret/)
- [kubectl create secret generic — referência](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/kubectl_create_secret_generic/)
- [Criptografar dados em repouso](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/)
